# Taste
- Prefers local-first workflows that treat shared/scarce resources (environments, compute slots, etc.) as things to hold only when truly necessary: do as much work locally as possible, and on failure release the resource and continue locally rather than holding it idle or repeatedly re-acquiring it. Confidence: 0.65
- Wants the design/proposal reviewed and approved by them before implementation begins (e.g. writes "design this, I'll review, then you develop"). Prefers a concrete written plan with explicit decision points for them to sign off on over jumping straight into coding. Confidence: 0.9
- Prefers real-time, push-based observability (SSE/WebSocket server-push) over interval polling / periodic refresh for monitoring, and wants observation to be comprehensive/complete rather than partial. Confidence: 0.7
- Commits and pushes completed work to git before moving on to new feature/development work, and expects the push to the remote repository to happen as part of finishing a task without being asked (e.g. "start development, then push to the remote repo"; also "find the problems, fix them and commit directly"; also "when done, push to git"). Confidence: 0.8
- Prefers outputs of expensive tool calls / analyses to be persisted to local files (per-artifact directories, plus an index file) so later reads/greps hit disk instead of re-invoking the tool or re-loading results into context; the archive should be reusable across resumed runs so analysis is never repeated. Confidence: 0.75
- Prefers additive changes: when introducing a new mechanism, keep the existing capability available as a fallback for cases where it's still useful rather than removing or fully replacing it (e.g. retain the Ghidra MCP for interactive queries even after adding local-file archiving). Confidence: 0.6
- Prefers precise/exact mechanisms over approximate heuristics when both are offered, even when the exact option costs extra integration work (e.g. chose per-request exact attribution via injected per-worker config over a zero-change text-scanning heuristic). Confidence: 0.6
- When a data-format mismatch surfaces, prefers fixing it at the source — specifying the format explicitly in the producer's prompt/config (defining exactly how the file must be maintained) — over making the consumer/parser more tolerant and guessing. Favors a strict, documented contract that producers must follow rather than defensive parsing. Confidence: 0.75
- For web dashboards/UIs, prefers building on an established shadcn/ui admin template stack (React + Vite + TypeScript + Tailwind + shadcn/ui) rather than a custom bare-bones UI. Confidence: 0.6
- Willing to accept a local build step (npm) for a web frontend when it enables using an established framework/template, rather than insisting on a zero-build single-file page. Confidence: 0.6
- Prefers the simplest adequate implementation and rejects over-engineering ("不用太麻烦"): when two approaches reach the same outcome, picks the one with less integration/setup work. Confidence: 0.6
- Is cost-sensitive about instrumentation/monitoring: only adopts a feature if it adds no meaningful overhead (no extra requests, tokens, or bandwidth); if it costs something, drops it. Confidence: 0.65
- Prefers user-facing data (e.g. chat/conversation history, logs, notes) to be persisted locally and restored so it survives page refreshes, restarts, and even backend/gateway restarts rather than being cleared. Confidence: 0.75
- In log/feed/chat UIs, wants the newest entries shown at the top (reverse-chronological / newest-first ordering) with the view scrolled to the newest on arrival — explicitly prefers this over the conventional bottom-appended chronological order. Confidence: 0.75
- Prefers to route user-initiated operations through the system's single existing command channel (e.g. having the customer agent perform everything via its normal request queue) instead of adding a separate control/bypass interface that could conflict with the existing state machine; favors "let the existing agent do it all" over new direct-control paths. Confidence: 0.55
- Environment: has a local HTTP proxy available on 127.0.0.1:7897 and wants it used to speed up slow network operations (npm install, git clone/push, etc.) on their Windows match instead of waiting on the direct connection. Confidence: 0.75
- Expects fully autonomous execution: given a goal, the agent should build/implement it, test it end-to-end itself, diagnose and fix whatever is broken, and only then commit — without stopping to ask for each step. A deliverable is not "done" until it has actually been run and its defects repaired. Confidence: 0.85
- Prefers end-to-end validation over unit-level checks: to verify a system that depends on external services, build a local stand-in for those dependencies (fake platform/mock upstream/simulated environment) and drive the whole flow through it, rather than testing components in isolation. Confidence: 0.7
- Communications are in Chinese and expects the assistant to reply in Chinese. Confidence: 0.7
- Wants to visually inspect a running UI themselves: expects the agent to actually launch the full stack (frontend + any backends/dependencies) and leave it serving locally so they can look at the result in their browser, rather than only hearing that it builds/works. They then check it personally and report discrepancies they spot (e.g. a page listing only one category of data) for the agent to investigate at the root cause. Confidence: 0.7
- Expects the UI to be refresh-safe and accurate: after a browser reload, displayed state (process/worker liveness, recent history) must reflect the real current backend state and populate immediately on mount, not be wrong or wait on the next push/stream frame. Confidence: 0.6
- Memory-sensitive about heavyweight tools: with multiple parallel workers, does not accept one heavy instance (e.g. a Ghidra/JVM) per project/worker; prefers consolidating it into a single shared long-lived service that all workers call. Confidence: 0.75
- Treats memory footprint as a primary criterion for choosing tools under a hard resource budget (e.g. ~4GB RAM per container): will abandon a featureful but heavy tool (Ghidra/JVM) for a far lighter one (binutils/objdump/readelf) even at the cost of losing capability (no decompiled pseudocode), and proactively asks whether alternatives (e.g. IDA) would use less memory. Confidence: 0.7
- Wants specialized heavy work separated out into a dedicated component (a purpose-built side service) rather than being performed ad hoc by each worker. Confidence: 0.55
- Wants exports of analyzed artifacts to be truly exhaustive — full function set plus disassembly/assembly, not a partial or summary-only subset. Confidence: 0.6
- Prefers heavy on-demand tooling (e.g. a Ghidra/JVM analysis run) to run to completion and then fully exit, freeing memory, while persisting its analysis results to an on-disk cache so later runs reuse it instead of re-analyzing — favors "finish work, save cache, exit" over a process that stays resident and continuously consumes memory. Confidence: 0.6
- When a heavy shared resource (e.g. a Ghidra/JVM analysis) must be used, prefers a single serialized access point: all workers request it from one place and block/queue when it's busy, then continue once their turn comes — rather than letting them run concurrently. Willing to trade waiting time for a bounded peak memory. Confidence: 0.6
- Wants the agent's container image to ship a standard toolchain out of the box rather than assuming tools can be installed on demand: explicitly asks for common pwn/web tooling (gdb, qemu, etc.) to be preinstalled in the solving agent's Docker image. Confidence: 0.65
- Validates the whole system against a broad, mixed-category benchmark rather than a single case, and deliberately escalates difficulty: asks for a batch of multiple challenges spanning categories (e.g. 10 tasks, 5 web / 5 pwn) that are harder than previously solved ones, to prove the pipeline really works end to end. Confidence: 0.6
- Prefers keeping the agent's container image lean: approves only the minimal set of essential tools and rejects optional/bulky additions even when they add capability (e.g. trimmed a proposed list down to just gdb-multiarch + qemu-user-static for pwn and dropped mitmproxy for web, cutting pwndbg/z3/libc6-dbg/qemu-system). Confidence: 0.65
- Wants evaluations run blind so they measure genuine solving ability, not just pipeline flow: no hints, no human intervention, and nothing that reveals the solution path to the agent under test. Reference exploits/solutions must be kept strictly out of the agent's reach — not in the image, not as platform attachments, and not as hints. Confidence: 0.8
- Wants each log entry to carry and display the timestamp of when it was emitted (not just the content), so the log is time-ordered and readable. Confidence: 0.6
- Wants status/monitoring displays to report precise, distinct states rather than one coarse ambiguous label: when a single indicator (e.g. "dead") lumps together genuinely different conditions (already-solved and exited, not-yet-dispatched, round-finished-awaiting-resume, killed/terminated), expects it broken down into the actual underlying state so the view reflects the real reason. Confidence: 0.55
- When asked to test/verify, expects the verification to be full-stack and multi-dimensional in one pass — not just that the tools run, but that the designed concurrency/serialization actually takes effect (e.g. fire concurrent requests and confirm they queue/serialize rather than run in parallel, measure wall-clock, check for leaked processes) and that the frontend has no anomalies — all before the work is considered done. Confidence: 0.65
- Expects long-running work to never stall the orchestrator's control loop: state checks should be one-shot snapshots (ps / grep / ls) followed by an immediate return, with any waiting delegated to an external periodic-resume mechanism — explicitly rejects synchronous blocking/polling loops (e.g. `for i in $(seq …); do …; sleep 20; done`, `while true`, `tail -f`) that freeze the agent and delay handling of finished work (reportedly an env sat unreleased ~8-10 minutes after its challenge was already solved). Confidence: 0.6
- Regularly reads the running system's worker logs/log files and, on spotting anomalies, expects the agent to work out the genuine root cause and explain it back in plain terms — explicitly separating real environment/tooling faults (e.g. unset TERM, blocked ASLR disable, debuginfod hanging) from the agent-under-test's own scripting/timing mistakes — rather than merely restating the error. Confidence: 0.55
